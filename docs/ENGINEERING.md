# Engineering standards & design principles

> What this project actually practiced, and what it deliberately skipped — the honest version,
> not the version that only lists successes. See [DECISIONS.md](./DECISIONS.md) for individual
> tool choices; this is about _how_ the code was written, not _which tools_ were picked.

---

## Design principles followed

| Principle                                                             | Where it shows up                                                                                                                                                                                                                                                                                     | Why it mattered here                                                                                                                                                                                                                                                                                                           |
| --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Surface real limitations, never hide them**                         | Verify's `hasCitations: false` is treated as a real signal, not swallowed; `07-generate/README.md` documents the local model's citation-format miss as a measured fact; `docs/ARCHITECTURE.md` explicitly marks what was planned but never built, instead of quietly describing it as if it existed   | The single biggest recurring failure mode in this kind of system is confident-sounding wrongness. Every stage that could produce one was built to say so plainly instead.                                                                                                                                                      |
| **Idempotency by construction**                                       | Chunk ids are deterministic (content/path-hash); repo ids are deterministic (`slug + sha256(source)`); re-indexing upserts, never duplicates (proven in `index.test.ts`)                                                                                                                              | A crashed or repeated ingest run converges to the same state instead of needing manual cleanup — cheaper than building a rollback/dedup step later.                                                                                                                                                                            |
| **Cache the resource, never cache the failure**                       | `embedder.ts`, `reranker.ts`, `llm.ts` (model-load promises), `vector-store.ts`'s `getSharedVectorStore`, `lexical-store.ts`'s `getCachedLexicalIndex`, `ask-stream.ts`'s `askCache` — every one of these caches only on success and clears itself on the matching failure or invalidation event      | A caching bug here doesn't corrupt data, but a _sticky failure_ (a transient network blip permanently breaking a stage until process restart) is a real, easy-to-miss footgun — this was actually found and fixed mid-project (see the code review that flagged it), then applied consistently to every cache added afterward. |
| **Guard by verification, not by trust**                               | Verify checks every citation against the exact context the model saw, not the whole repo; `MAX_INDEXED_REPOS` + LRU eviction bound an unauthenticated `/index`; Fastify JSON-schema validation rejects malformed request bodies before they reach the pipeline                                        | An unauthenticated demo server needs guardrails that don't depend on the caller behaving — cheap, mechanical checks instead of "we'll just trust the input."                                                                                                                                                                   |
| **One stage, one job, composed linearly (with one deliberate cycle)** | The 4-stage ingest pipeline and 8-stage query pipeline are each a chain of narrow, single-purpose functions (`RouteResult in → RetrieveResult out`, etc.); Grade→Retrieve is the one intentional cycle, justified in `DECISIONS.md #0006`, not organically grown                                      | Easiest architecture to reason about, test in isolation, and explain — every stage has its own README, own tests, own "what feeds this / what this feeds" note.                                                                                                                                                                |
| **Progressive disclosure over always-on noise**                       | The UI shows the answer and a one-line citation summary by default; the full reasoning trace (route, hops, retrieved chunks, citation checks) sits behind a single "Show pipeline trace" toggle, collapsed by default; a citation line doesn't render at all when there's nothing to report           | Learned live, from actual user feedback during this build: an always-visible warning badge read as an error even when the answer was fine — the fix was information architecture, not wording.                                                                                                                                 |
| **Test what's real, mock only what you must**                         | Nearly every "does the wiring work" test runs the real embedder/reranker/local LLM rather than mocking them; fakes appear only where a specific unit needs isolating from a slow/nondeterministic dependency (e.g. `answer.test.ts`'s fake `generateFn`), and that's stated in the test's own comment | Mocked integration tests are exactly what let two of this project's real bugs (the SSE `hijack()`/CORS issue, `discover.ts`'s locale-sort) slip past `.inject()`-based and unit-level tests — both were only caught by testing against a real browser or real filesystem.                                                      |

## Engineering standards followed

- **Type safety**: TypeScript strict mode across the whole codebase; ESLint + Prettier enforced as a gate before any stage is considered done (see `CLAUDE.md`'s stage-completion checklist).
- **Test discipline**: 171 tests as of this writing, spanning unit (route/grade/expand heuristics), integration (real embedder/reranker/LLM calls), and end-to-end (a real HTTP request through the Fastify server). No stage shipped without its own test file.
- **Documentation-as-you-build, not after**: every pipeline stage has a README with a _real, captured_ example run against a standard public test repo — never a hand-typed/synthetic example. Enforced as part of the definition of "done" for each stage, not written retroactively.
- **Decision records with rejected alternatives**: every major tool choice (`docs/DECISIONS.md`) names what else was considered and why it lost, plus a "revisit when" trigger — not just the winner.
- **Adversarial self-review**: multiple structured code-review passes during the build (correctness, cleanup, conventions, altitude) turned up and fixed real bugs — a falsy-zero port bug, an unguarded SSE write, a stale-clone-reuse bug, a dedup-order bug in Expand, among others — rather than only reviewing for style.
- **Honest doc-vs-reality audits**: a dedicated pass caught and corrected several places where documentation described the _originally planned_ architecture (LangGraph, a ports/adapters layer, an eval harness) as if it had been built, when it hadn't — corrected to state plainly what's real vs. planned.

## Engineering standards skipped — deliberately or for time

- **No CI/CD pipeline** — tests are run locally (`npm test`) before every stage is marked done, but there's no GitHub Actions (or equivalent) enforcing this on push. For a real team project this would be the first addition.
- **No formal retrieval eval harness** — the plan called for a golden question set scored with recall@k/MRR/nDCG; `eval/` exists as a directory but was never populated. Real captured per-stage examples substitute today — honest, but a weaker signal than a repeatable metric.
- **No ports & adapters abstraction**, despite being planned — every stage imports its concrete tool (LanceDB, MiniSearch, `node-llama-cpp`) directly. Documented as a deliberate, acknowledged simplification for a project this size (see `DECISIONS.md`'s drift note on ADR #0009), not an oversight.
- **No incremental indexing** — re-indexing a repo does a full rescan (cheap only because of content-hash caching and idempotent upserts), not a real `git diff`-based changed-files-only pass.
- **No auth/authorization on the API** — anyone who can reach `/index` can index a repo; `MAX_INDEXED_REPOS` bounds the blast radius but doesn't gate who can trigger it. Fine for a local demo, a real blocker for anything multi-tenant.
- **No structured logging or production observability** — no request tracing, no metrics export, no log aggregation; `console.log`/Fastify's own defaults only. `docs/ARCHITECTURE.md` names Langfuse as the intended swap, but it isn't wired up.
- **Minimal frontend test coverage** — no component-level tests for the React UI (no `@testing-library/react`/jsdom in the project); verified instead by driving the actual app in a real browser during development. A real gap for regression safety going forward.
